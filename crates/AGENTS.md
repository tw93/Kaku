# Crates Agent Guide

`crates/` contains shared utility crates used across the workspace. Inspect the target crate's `Cargo.toml` before editing because Kaku keeps some WezTerm-derived crates and adds its own helpers over time.

## Scope

Key groups:

| Group | Crates |
|-------|--------|
| Terminal core | `codec`, `color-types`, `vtparse`, `wezterm-cell`, `wezterm-escape-parser`, `wezterm-surface` |
| GUI and input | `wezterm-font`, `wezterm-input-types`, `wezterm-gui-subcommands`, `wezterm-open-url`, `wezterm-toast-notification` |
| Mux, client, and remote | `wezterm-client`, `wezterm-mux-server-impl`, `wezterm-ssh`, `wezterm-uds`, `kaku-relay`, `kaku-remote` |
| Platform and process | `pty`, `filedescriptor`, `procinfo`, `env-bootstrap`, `umask`, `async_ossl` |
| Lua and config support | `luahelper`, `wezterm-dynamic` |
| Shared utilities | `promise`, `base91`, `bidi`, `bintree`, `frecency`, `lfucache`, `rangeset`, `ratelim`, `tabout`, `wezterm-blob-leases`, `wezterm-char-props`, `wezterm-version` |
| Kaku-specific utilities | `kaku-ai-utils`, `kaku-unicode-names` (Unicode name table for the character selector, a zstd-compressed `src/names.tsv.zst` decoded on first use; regenerate with `regenerate.sh`, do not hand-edit) |

## Practical Rules

- For macOS notification actions that launch Kaku commands, prefer resolving bundled executables relative to the running `kaku-gui` binary.
- Keep `kaku-ai-utils` provider-agnostic; provider policy belongs in GUI/CLI call sites and config, not in low-level helpers.
- When shared cache helpers affect startup, verify the GUI consumer and avoid invalidating hot-path caches unnecessarily.
- `wezterm-escape-parser` ProgramStatus accepts whitespace around key/value pairs and skips lexically malformed optional pairs without losing valid state. Preserve decoded-text control-character and size checks; permissive pair parsing must not weaken those boundaries. Regressions live in `src/osc.rs` (`program_status_trims_pair_whitespace`, `program_status_skips_malformed_optional_pairs`, and `program_status`).

## Web Terminal and Relay

`kaku-remote` serves a browser terminal (`src/web.rs`, page in `assets/web/`) and `kaku-relay` lets it be reached from outside the LAN (`src/share.rs` on the Mac side). The `remote` cargo feature is on by default in `kaku` and `kaku-gui`, so Release and Nightly ship it; the feature itself stays off until the user turns it on. Invariants:

- Launched in testing, free (2026-10-17): every build carries the web terminal, `remote.enabled` defaults to false, and `kaku remote` asks before turning it on, so nothing changes for a user who never runs it. The private-build machinery (`nightly.sh --private`, the `check_no_web_terminal.sh` publish guard, `release.sh` refusing the feature, `kaku remote` hidden from `--help`) was removed at launch. Remote access remains free, including the relay paid for by the maintainer; do not add paid tiers, accounts, usage metering or registration tokens.
- Off until the user turns it on (2026-10-16): `remote.enabled` defaults to false. `kaku remote` asks before turning it on and writes `config.remote = { enabled = true }` to the user's kaku.lua through the settings screen's line writer (`config_tui::set_remote_enabled`); `kaku remote off` writes false. Neither rewrites a `config.remote` table that holds other keys (a relay of their own), which a whole-line rewrite would drop; they say to edit it instead. The bridge follows config reloads (`follow_config`): it starts when the setting turns on, without restarting Kaku, and when it turns off its runtime is dropped, which ends the relay link and every web session within a second, and the state file is removed so `kaku remote` no longer sees sharing. Verify off/on transitions in the same process; restarting the app does not test release of `remote.lock`.
- One Kaku per data directory serves remote access (2026-10-19): `launch_when_sole` holds a `flock` on `DATA_DIR/remote.lock`; a second GUI on the same data directory (a build-folder copy, another `kaku start`) waits and takes over when the first quits. Before this, a second copy registered with the relay under the same identity and took the browser over to its own terminals. Drift checks name the frame the page drew (`seq`, `Shown::rows_after`), so they still run while frames are in flight over the relay; checking only with nothing in flight never ran while Claude Code worked.
- No LAN access (2026-10-16 decision, replacing the 2026-10-15 opt-in): the local server listens on 127.0.0.1 only and `remote.bind` is deprecated and ignored, kept so configs that set it still load. The maintainer has no use for it at home and it was plain HTTP: `http://192.168.x.x` is not a secure context, so `crypto.subtle` is missing (measured in Helium), and the relay's https page cannot open a `ws://` LAN socket (mixed content). Do not bring LAN access back.
- The local server answers only requests whose `Host` is its own (`127.0.0.1`, `localhost` or `[::1]` with the listener's own port, so a config reload that edits `remote.port` does not lock the page out), so a web page that rebinds its name to 127.0.0.1 cannot read same-origin responses. No route serves the token: `kaku remote` reads it from the 0600 state file. The routes for the old iOS client (`/api/config`, `/api/panes`, `/qr` with the token, `/ws/{pane_id}`, and the `ai_chat` handler in `kaku-gui/src/ai_remote.rs`) were removed on 2026-10-14 with the maintainer's approval: its relay mode had already stopped working, and `/qr` handed the token to any local process, other macOS users included. A future iOS app should speak the web terminal's protocol or wrap the page, not bring these back.
- A session ends after `SESSION_SILENCE` (180 s) without a message from its browser, so a half-open socket from a sleeping laptop does not hold App Nap off forever.
- One session per browser, carried either by the local WebSocket (`#t=<token>` link) or by the relay (a paired browser, see below). `run_session` sees transport-neutral input and output queues; keep socket and encryption logic out of it.
- The page mirrors Kaku's own terminal model as ANSI frames rather than replaying the PTY stream, so terminal queries are answered once, by Kaku. Keys go through `Pane::key_down`, pastes through `send_paste`, and already encoded text through `send_text`. Local panes use the terminal's existing ordered background writer for all three; never send Remote text directly to the blocking PTY writer.
- Kaku Assistant's chat is a GUI overlay that never reaches the mux, so the page would show and type into the shell under it. The GUI reports it with `set_ai_chat_open` (open, close, and a chat dropped on config reload); while it is open `handle_input` drops typing, pastes and clicks for that pane, an upload is saved without pasting its path, and the page dims the pane with a notice. Chat on the page itself was declined (2026-10-18): it would be a second chat UI, and using it from a browser reads as odd; do not build one.
- Anything that reads the Lua config (for example `can_close_without_prompting`) must run on the GUI thread via `promise::spawn::spawn_into_main_thread`; calling it from the server's tokio threads panics.
- Relay ids are the first 128 bits of SHA-256 of a secret the Mac sends only to the relay when it registers (`x-kaku-secret`, over TLS); the relay checks it against the id and keeps nothing, so nobody else can register as that Mac. The secret proves the id, not the Mac: pages trust only the Mac's signing key, so a leaked secret can take the id offline but opens no terminal. Through the relay only paired browsers get a session (`src/pairing.rs`, 2026-10-15; the old `#k=<key>` link, one AES key for every browser, is retired and its pages are told to reload). `kaku remote` writes a one-time offer (`remote-pairing.json`, 10 minutes) and prints `/{id}/#p=<secret>&m=<Mac public key>`; the page makes a non-extractable ECDSA P-256 device key and keeps it in IndexedDB once Kaku has admitted it. Each connection: Kaku sends `KCH3` and an ephemeral P-256 key in the clear, the page answers `KCB3` and its own, both derive one AES-256-GCM key per direction by HKDF-SHA256 over the ECDH secret salted with the transcript (SHA-256 of `kaku-remote v3`, the relay id, both ephemeral keys). Kaku's first sealed message signs the transcript with its long-term key (`mac_key` in `remote-share.json`), which the page checks against the key from its pairing link before sending anything, so a relay cannot pose as the Mac; the page's first sealed message signs it with its device key (`auth`), adding an HMAC of the transcript under the offer secret the first time (`pair`). Messages carry their direction label and position as associated data. Close codes: 4403 not a paired browser, 4401 pairing link expired or used, 4409 pairing not confirmed on the Mac, 4429 pairing link already taken by another browser, 4426 page from before pairing, 4408 no proof in time; the relay must pass each through (`browser_close`), or the page reads it as busy and retries. A bare 4403 can come from a relay, so the page keeps its key and retries, and forgets it only after Kaku's sealed `revoked` message; three bare 4403s in a row stop the retries but keep the key. A pairing link is confirmed on the Mac (2026-10-26), so whoever gets hold of the link cannot pair alone: the first browser to send a valid proof holds the link (`remote-pairing-request.json`; any other browser gets 4429), Kaku seals `pair_pending` to it, and both `kaku remote` and the page show the same six-digit code, an HMAC of the browser's device key under the offer secret. Enter in `kaku remote` allows it, Ctrl+C or the offer's 10 minutes refuse it (4409), and either way the link is used up. Messages the page sends while waiting are held (16 at most) and fed in once it is allowed, and the session's sequence numbers start after `pair_pending`. A paired device connecting again after 30 minutes away posts a macOS notification (`QUIET_RETURN`; reloads and reconnects stay quiet), which is the Mac-side sign of remote use (no menubar or tab bar mark, by the maintainer's choice on 2026-10-15), and `kaku remote devices` / `kaku remote revoke <id>` list and remove devices (sessions of a removed device end within seconds). ring's ECDH takes only ephemeral keys, which is why long-term identity is a signature, not a static DH key; ring's fixed ECDSA signatures and WebCrypto's are the same r||s form.
- Each web session holds `awake::Awake`, a latency-critical `NSProcessInfo` activity. Without it, App Nap throttles the backgrounded GUI's main thread, which turns PTY output into the pane change the session renders from, and every echo waited 100-200 ms. Measure remote input latency with the Kaku window hidden, not focused.
- `Shown::update` turns a screen whose rows moved into `CSI n S` / `CSI n T` plus the new rows. That relies on each row starting with its own `CSI row;1H` and on the page never setting a scroll region; keep both, or the browser's copy drifts from Kaku's.
- Clipboard writes from programs (OSC 52, `MuxNotification::AssignClipboard`) also go to browsers viewing that pane (`web::publish_clipboard`, 1 MB cap); the Mac clipboard keeps getting them. Find (`Search`) runs on the Mac over the pane's history, so it reaches past what the page shows. Files a browser drops or pastes arrive in chunks, in a bounded 512 KiB window of 16 KiB chunks, each acknowledged (`UploadAck`), so its percentage is what reached the Mac; a session that ends mid-file deletes the partial file (`Uploads` drop) and the page resends after reconnecting. Files are written to `~/Downloads/Kaku` under a sanitized, de-duplicated name (`safe_file_name`, `unused_path`, 50 MB cap), and their path is pasted into the original drop pane with `quote_dropped_files`, as a native drop would be.
- Scrolling a plain shell (`local_scroll` in each frame: no alternate screen, no mouse grab, and no foreground `less`) never round-trips: the page fetches history rows with `History` in pages of `HISTORY_PAGE` and scrolls them in `#past`, laid exactly over the terminal with each run placed at Kaku's column. Programs that take the mouse or the alternate screen still get the scroll on the Mac; `less -X` also receives scroll keys, as in the native wheel handler, and Find still pins the Mac-side view (`View::pinned_top`).
- The page names tabs by `tab_id` and reorders them per `window_id`; rename and move go through `TabAction::Rename` / `TabAction::Move` in `kaku-gui/src/remote_tabs.rs`, which keep the Mac's active tab. A split tab lists its `panes`; viewing one sends `Activate`, which also focuses that split on the Mac. A split tab keeps the Mac window's size (`split_claim`): the browser claims nothing for it, shows the viewed split at its own size scaled to fit the page (up to twice Kaku's font size), and a tab a browser had sized is handed back to its window once split (`TabAction::Reclaim`). Growing the tab by the split's share, as before 2026-10-19, pushed the other splits out of the Mac window. Size claims use zoom-aware `iter_panes()` geometry, so a zoomed pane is claimed like a lone one; tab navigation still lists hidden splits. Browser zoom and unzoom carry only the viewed pane's current claim and reapply it synchronously after the GUI toggles zoom; another pane's action cannot borrow that claim, and native or other-client geometry changes do not automatically reclaim the browser viewport. Frame rendering runs on another thread, so the GUI callback is not a cross-thread atomic transaction.
- Web pane menus retain the selected `pane_id` through clipboard permission prompts and close dialogs. Splits call `Mux::split_pane` with that id rather than the deferred active-pane spawn path. Confirmed pane closes remove that exact pane, or record and remove its tab when it is last; `CloseCurrentPane { confirm: false }` is not sufficient under `AlwaysPrompt`. Middle-click tab close shares the existing browser confirmation path. Optimistic tab closes require a connected transport and a timer that restores the latest authoritative list when the close is not confirmed; the server suppresses identical lists, so expiry must not depend on another list arriving. Keep cached pane snapshots until the authoritative list drops their pane. Keep native phone selection menus intact.
- Web URL detection stops at CJK sentence punctuation and unmatched closing wrappers, retains balanced path parentheses, and maps UTF-16 regex offsets back to terminal cells, including surrogate pairs and wide end cells. The browser regression fixture includes the reported GitHub comment link followed by `)，并以`.
- A tab a browser sized keeps that size through relayouts the Mac does on its own (display or scale change, focus, config or theme reload, tab bar visibility): `apply_dimensions` asks `window_relayout_resizes_tab` per tab. Only the Mac's own use takes it back: typing or clicking (`reclaim_active_tab_size`) or a live window drag. Focus and a modifier pressed alone do not count (2026-10-19): switching between a fullscreen browser and Kaku with Cmd+Tab resized the tab on every switch, and Claude Code left a copy of its output behind for each size. Resizing it under the browser made Claude Code and Codex redraw for the Mac's rows and jump up in the page. The desktop view's synthetic input counts as the Mac's, so the page claims its grid again on its next input and when it leaves the desktop view (`macSized`, `takeBack`). After a reload the first frames still carry the Mac's grid until the new claim lands; the page keeps the terminal at opacity 0 (`body.sizing`, still focusable, unlike the pre-first-frame `visibility: hidden`) until a frame has the claimed grid or a split's own, for at most `REVEAL_WAIT` (600 ms). Tests that screenshot the terminal wait for it to fade in (`fadedIn`: `sizing` cleared and `#term` at opacity 1); a screenshot during the 0.2 s fade failed the icon redraw test on every CI run from 2026-10-23.
- Page fonts: the page draws with the families of Kaku's `config.font` in order (`font_families`; JetBrains Mono maps to the bundled `Kaku Mono`, emoji fonts stay unnamed), then its own fallbacks with `Kaku Symbols`, the bundled Symbols Nerd Font limited by `unicode-range` to its private-use spans so it is fetched only when an icon shows. Fonts the user installed are resolved on the Mac the way Kaku renders (`src/fonts.rs`: `font_dirs`, then CoreText) and listed in `font_files`, text weight only, since the page draws bold at that weight; files under `/System/`, collections and anything over 32 MB are left out. The page fetches a listed file over the download path only when the browser lacks the family, and keeps it in Cache Storage keyed by path, size and date. The WOFF2 files in `assets/web` come from `scripts/build_web_fonts.py`; rerun it when `assets/fonts` changes, and print its `unicode-range` into `index.html`.
- The relay is public and sheds abuse itself: browser messages are capped at 512 KB and Mac messages at 4 MB, frames too (`max_frame_size`: tungstenite buffers a whole frame, 16 MB by default, before it checks the message cap); bytes queued toward one Mac (`HOST_QUEUE_BYTES`, the flooding browser is dropped) and toward one browser (`BROWSER_QUEUE_BYTES`, the stalled page is dropped) are bounded, and so are all queues together (`GLOBAL_QUEUE_BYTES`): a message count alone let one stalled page hold a gigabyte of 4 MB screens on a 256 MB machine. Every queue gives its unsent bytes back when its socket ends (`Queued`'s `Drop`), or the relay-wide budget leaks until nothing is accepted; at most 2 registrations per id (a third evicts the oldest) and 4 browser sockets per client address per host; when a host's 8 browser slots are full, a socket the Mac has not admitted is let go (`make_room`; the Mac sends `{"t":"ok","c":c}` once it admits a browser), so sockets that only know the id cannot lock the owner out; the one let go has come the shortest way through the handshake, oldest first, since one still open after its hello and proof is a real browser, perhaps waiting for its pairing to be confirmed; before `ok` a browser passes the Mac at most `PENDING_MESSAGES` (8) messages and `PENDING_BYTES` (16 KB), the handshake plus the `hello` and `attach` the page sends behind its proof, and past that the relay stops reading it until admission rather than closing it, for at most `PENDING_LIMIT` (11 minutes, longer than a pairing offer lives); new browser sockets per host are limited (`JOIN_BURST` 12, then one every 2 s) before the upgrade, except from addresses one of its browsers was admitted from; each Mac's link carries at most `HOST_RATE` (3 MB/s, 32 MB burst, 1 MB at connect) each way, paced by reading the sender more slowly, which a desktop view or a 50 MB download stays under; requests get `HEADER_READ_TIMEOUT` (20 s) for their headers (`serve`; `axum::serve` gives hyper no timer, so it had none); the relay runs as a non-root user; devices are matched on their whole public key, never the 8-hex id people see; `remote-devices.json` changes under an `flock` (`update_devices_at`) so a sign-in cannot write a revoked device back; hosts silent for 75 s and admitted browsers for 150 s are closed. The relay serves the page and its files from its own copy, built in from `crates/kaku-remote/assets/web` (`page_file`), and asks no Mac for them; the page itself answers 404 with the offline notice while the Mac is away, which an open page relies on to tell an offline Mac from a network problem. So a relay deploy ships the page: deploy it together with Kakus that speak its protocol (pairing, `KCH3`), never ahead of them. `fly.toml` caps connections at 400 (soft 300), about 200 people online, from a release-build load test (400 Macs plus 200 streaming pages at 88 MB); raise it only with a new load test or a larger machine, and the Docker build uses `Cargo.lock` with `--locked`.
- The page lives on its own origin, `t.kaku.fun` (2026-10-16), so serving a page that misuses the browser's keys takes a compromise of that origin, not just of the relay. `scripts/publish_web_page.sh` builds it from `crates/kaku-remote/assets/web` and the bundled JetBrains Mono, fills the `kaku-relay` meta tag (empty in the copies Kaku and the relay serve, which then talk to their own origin), writes a `vercel.json` with `/<id>` and `/<id>/` rewrites, a CSP that allows the one inline script by its SHA-256, and no caching, and deploys it with `vercel deploy --prod` to the `kaku-web` Vercel project, which holds nothing else: a path on `kaku.fun` would share an origin, and the keys, with every page of the site. The page must keep exactly one inline script and no inline event handlers, or the script refuses to publish. With `KAKU_RELAY_PAGE_ORIGIN` set, the relay 308s its page addresses there (the fragment survives), serves no page files, admits browser sockets only with that `Origin` (others are upgraded and closed at once with 4426, so a page still open on the relay's origin from before the move says to reload instead of reading as no network), and answers `/<id>/status` (200 or 404, CORS for that origin) for the page's offline notice. Kaku links the default relay's page to `t.kaku.fun`, any other relay's to the relay itself. `crates/kaku-remote/tests/static_page.cjs` runs the published page behind a server applying its `vercel.json` and checks the redirect, pairing, bookmarks with and without the slash, a foreign `Origin` refused, and no CSP refusals; poll with `page.evaluate` there, since `waitForFunction` evaluates a string the CSP blocks. Publish the page before a relay deploy that sets the origin. After each reconnect the page fetches its own address and reloads when the inline script served there differs from its own (at most once per version through sessionStorage, so a stale cache cannot loop, and never while an upload runs), so tabs left open pick up a new page or a Kaku update without the user reloading; that fetch is why the published CSP's `connect-src` includes `'self'`.
- The Mac-screen view (2026-10-20) is the maintainer's own for now: the `desktop` cargo feature (`kaku-gui/desktop`) is off by default, so Release and Nightly never carry it. It needs a `kaku-desktop` helper, built from its separate repository. Private packages carry it in `Contents/MacOS/kaku-desktop`, preferred over the legacy copy at `config::DATA_DIR/kaku-desktop`; Kaku starts it as a child so macOS checks Kaku's own Screen Recording and Accessibility grants, and `src/desktop.rs` forwards only `desktop_*` messages in each direction, turning the helper's `desktop_frame` lines into binary messages (zero byte, u32 header length, JSON header, H.264 bytes) for a page whose `desktop_start` says `binary`; `run_session` takes them on a separate `frames` channel that both writers (`share.rs` and the local WebSocket) merge. The helper lives as long as the page's session: `desktop_stop` is forwarded, not acted on, because the helper may hold a virtual display shaped to the page's view, and making one again on every visit costs seconds and moves the Mac's windows (`the_helper_outlives_a_stop_but_not_the_session`). The page loads `assets/web/desktop.js` only when the session config says `desktop: true`, so other Kakus and the published page show nothing new. Build the helper in Release first, then build the private package with `PROFILE=release-opt CARGO_FEATURES=kaku-gui/desktop KAKU_DESKTOP_HELPER=<helper-executable> OUT_DIR=dist/private ./scripts/build.sh --app-only --native-arch`. The build checks helper architecture and signs it before the main executable. Public builds omit both the feature and helper input; a public update replaces the private package and removes its desktop capability. Preparing a private package does not authorize replacing or restarting the installed app.
- Desktop feedback timing names two boundaries: `desktop_input_ack` confirms a successful input post, and a drawn frame with its `input_seq` confirms a capture after that post, not that the target app reacted. Match both even when independent output queues deliver the frame first; retain slow samples and report unposted, unframed and cancelled inputs separately. A new `stream_id` isolates capture generations and decoder callbacks; frame sequence numbers remain monotonic within the helper. ACK old frames with their own stream id, never the current one. Legacy helpers without these fields stay usable without fabricated timing. Desktop wheel, touch and pointer cancellation belong only to the visible desktop, never the hidden terminal. While the Mac is locked the helper sends `desktop_locked` (from `CGSSessionScreenIsLocked` plus the `com.apple.screenIsLocked` / `screenIsUnlocked` notifications, watched only between `desktop_start` and `desktop_stop`) and the page shows a notice over the picture; typing the password into the view unlocks it.
- Direct path (2026-10-21 for the desktop view, every build and session since 2026-10-22, `src/p2p.rs` and the page's «Direct path» block): beside the relay, the page offers a WebRTC data channel (str0m with `rust-crypto` on the Mac; `apple-crypto` fails to link) once the config says `direct` (or `desktop`, from the private builds that had it first; a Kaku that says neither gets no offer); offer and answer travel inside the sealed session, so the relay cannot sit in the middle. Interactive replies (terminal frames included), the page's messages under 16 KB and desktop pictures take it, files stay on the relay. Each path has a number (`id` in `rtc_answer`). Order across the move is a fence, not a guess: each side's last relay message before it sends on the path is `rtc_ready` (Kaku sends one per lane, text and frames, the frames one as a binary header-only frame), and the receiver holds what arrives on the path until that marker comes through the relay; without it a delta picture or a key-up overtook one still on the relay. Either side ending a path tells the other by the relay (`rtc_closed` from Kaku, `rtc_close` from the page): the page's channel otherwise stayed "open" for about 30 s after Kaku dropped it and lost every click. After a path that had opened ends, the page sends `hello` and `attach` (what was on the path is lost, so the screen starts over), asks for a key frame, and offers again after 2, 5, 15, 30, 60 s; a path that never opened is not retried. Kaku tells the helper `desktop_keyframe` with `path_changed` on every move, which drops in-flight pictures and the old path's round trip and rate samples (kept, a 5 ms direct RTT read every 120 ms relay ack as a standing queue). Host candidates from `getifaddrs` minus loopback, link-local and 198.18/15 (TUN fake IP), plus one server-reflexive candidate per socket from a STUN binding to `stun.cloudflare.com`, `stun.l.google.com` and `stun.miwifi.com` (the page asks the same three; pinned from Hangzhou on 2026-10-26, Xiaomi answered in about 40 ms, Cloudflare in about 220 ms, Google sometimes never), sent before the socket's reader starts and given `STUN_WAIT` (800 ms, DNS included) in all. Without the Mac's reflexive address a browser behind a port-restricted NAT only ever sent to the Mac's private addresses and never opened its own NAT to the Mac. Each socket is pinned to the interface that owns its address (`IP_BOUND_IF`, `pin_to_interface`), so a proxy in TUN mode does not carry these datagrams; only these sockets, the relay link and other apps keep the proxy. Unpinned, Stash took them through a Japan node on 2026-10-26: STUN answered with the proxy's exit or not within `STUN_WAIT`, so the answer often held only private addresses, and a path that did open had a 4 to 5 s round trip through the proxy's UDP relay (from a page's `chrome://webrtc-internals` dump). Pinned, a Parallels bridge socket never hears STUN, so `reflexive_all` gives each socket its own deadline and keeps the answers that arrived. A STUN name that resolves only into 198.18/15 (a proxy's fake-ip DNS) is skipped and logged, since a pinned socket cannot reach it. The maintainer's home network maps each destination to a different public address and port even pinned past the proxy (China Telecom's own NAT, measured with one socket against four servers), so a direct path between two NATed networks can still fail and fall back to the relay. The log says how many public addresses the Mac offers and what kinds of candidates the page sent, counts only, and once the path opens, from str0m's per-second `PeerStats`, whether the selected pair crosses the local network, Tailscale or the internet and its round trip, no addresses. No TURN: when hole punching fails, the relay already carries the session. Unit tests keep STUN off (`STUN_SERVERS` is empty under `cfg(test)`); `public_stun` (ignored) asks the real servers. Pictures ride the reliable ordered channel on purpose, since H.264 deltas cannot survive loss. Every datagram goes through `Rtc::accepts` before `handle_input`: str0m otherwise lets any address that sends a DTLS ClientHello first become the DTLS peer and the path dies, so a stranger who learns the port could stop it, and the filter keeps only STUN and traffic from addresses that passed the ICE check (`a_strangers_handshake_sent_first_does_not_stop_the_path`). The page's `ping` never takes the path: the relay drops a browser it has not heard from in `BROWSER_SILENCE` (150 s), and with the path open nothing else reaches it, so idle direct sessions were cut and reconnected every 2 min 44 s (seen in production 2026-10-27).
- The relay runs in `nrt` (Tokyo, `crates/kaku-relay/fly.toml`), the edge the Mac enters through: from `sin` every keystroke and echo crossed Tokyo to Singapore twice, 375 ms echo against 166 ms now. It keeps hosts in memory, so run one machine; two would split a Mac and its browsers across them. The relay is not where time goes (2026-10-20): a release build forwards 150 Mbps from one Mac to one browser with under a millisecond added, and the live machine sat at load 0.00 while a page streamed. Slowness through it comes from each side's path to Fly: a proxy node can cap the Mac's upload far below its own line, and some direct routes from China enter a far edge such as `fra`. Measure the path (`fly-request-id` names the edge, a timed upload gives the rate) before resizing the machine or moving the region, and make streams adapt to the link rather than assume it, as the desktop helper's rate control does.
- Only Mac-confirmed text is rendered. Cursor visibility cannot distinguish normal input from passwords, so never predict typed characters. Pages opt into output flow control with `Hello.frame_ack`: at most 16 unacknowledged frames (the page acks every fourth frame or 300 ms after the first unacked one, so in flight reaches RTT/16 ms + 4 at 60 Hz; twelve stalled a stream past 128 ms) and a 512 KiB JSON byte waterline, including associated images. One complete frame may cross the waterline before rendering pauses; ACK after xterm parses even an ignored pane frame, coalesce later dirty output, and leave legacy hello clients unthrottled.
- Browser selection copying follows the Mac's existing `copy_on_select` value and runs on selection release without a network hop. Preserve manual copy when disabled, reconstruct history line breaks and virtual gaps, and never queue a denied automatic copy for a later unrelated gesture. Browser clipboard permission and real mobile selection remain browser-specific.
- `Frame.wrapped` and `History.wrapped` identify physical rows that continue into the next row. Copying, history pagination and pane snapshots preserve these flags; even a delta frame carries the whole array, and a wrap-only change must be sent. Never infer soft wrapping from a full-width row. Older hosts without flags retain hard line breaks.
- History keeps at most 10,000 row strings but materializes only visible rows and overscan, preserving stable DOM nodes that intersect an active selection. Cached tab attachment must precede resize, and an equal-size claim must still record browser ownership.
- Paths in the output (`~/…`, `/…`, `./…`, never inside a URL; `PATH_RE` in the page) are links: Cmd+click (Ctrl+click off the Mac) asks Kaku for that file (`Download`), and it comes back as a browser download. Kaku resolves `~` to the home folder and a relative path against the pane's working directory, sends only regular files up to 50 MB, and refuses folders and missing files by name. Chunks of 64 KB go out while less than `DOWNLOAD_WINDOW` (256 KB) is unacknowledged (`DownloadAck`), limiting queued bytes ahead of terminal interaction. The maintainer chose input and scroll responsiveness over bulk throughput on fast, high-latency links (2026-10-18); keep that trade-off explicit when changing the window. The relay never holds much of a file for one browser; the relay drops a browser past 8 MB queued. A download ends with its session, and the page says so on a dropped link. Any paired browser already has the shell, so reading a file grants nothing new.
- Upload transfer ids bind the file and original pane for ten minutes after completion, across transport reconnects within the same app process. Retry returns the receipt without writing or pasting twice; cancellation and disconnect remove only partial files. Freeze the target once for a multi-file drop.
- Access code (2026-10-16, the launch gate the maintainer chose over trials): with `KAKU_RELAY_ACCESS_CODE` set (a fly secret the maintainer picks), the relay registers only Macs presenting it in `x-kaku-access`, compared as SHA-256 in constant time; 401 bodies say `access code required` or `wrong access code`, and ten wrong codes from one address lock it for `ACCESS_WINDOW` (429). `kaku remote` reads the relay status, asks for the code without echo when the relay refused it, saves it to `remote-access` (0600, ASCII only since it travels in a header), and waits for the bridge, which polls that file during its backoff and retries within a second. Every recorded attempt stamps `RelayStatus::checked`, so a second wrong code is told apart from a stale one. Per-address limits sit beside it: `CONNECTS_PER_MINUTE` new sockets and `MAX_HOSTS_PER_ADDR` registered Macs per source, which `source_of` takes as the IPv4 address or the IPv6 /64 from `fly-client-ip` (r.kaku.fun has an AAAA record, and one IPv6 client can pick a new address from its /64 for every request); a large limits map is swept at most once a second; local runs have no client address and are not limited. Host admission must enforce both address and global capacity under the same lock as registration; a pre-upgrade count check alone is not a limit under concurrent handshakes. `live.cjs` runs its relay with a code and checks refusal, then acceptance after saving it.
- No registration tokens (2026-10-17): remote access is free, so the Ed25519 registration tokens built for trials and Pro (`kaku-relay keygen` / `issue`, `KAKU_RELAY_TOKEN_KEY`, `kaku remote --token`, `x-kaku-token` on registration) were removed with their `ring` and `base64` dependencies; the access code and per-address limits are what gate the relay. Measured cost at that point: one heavy user moved 271 MB a day through the relay (about $0.33 a month of Tokyo egress), so about 100 users cost $20 to $40 a month on the 256 MB machine.
- No pairing QR code (2026-10-17, maintainer's call): the page is made for a desktop browser for now, so `kaku remote` prints the link with how to use it and the manage commands, not a QR code; do not bring one back while phones are not a target. The link is only `#<one-time secret>` (`pairing::pairing_fragment`); `mac_auth` carries the Mac key, and while the offer is fresh a `tag`, HMAC under that secret over the transcript and the key (`pairing::mac_key_tag`), which the page checks before trusting the key. The relay never sees the secret, so it cannot vouch for a key of its own; a missing tag means the link was used or expired. The page still accepts the older `#p=<secret>&m=<key>` form. Publish the page before shipping a build that prints the bare form.
- Remote input stays ordered within each browser, but a blocked browser must not hold the shared relay receive loop. Each browser has a bounded worker; overload or timeout closes that browser explicitly rather than dropping individual keys. GUI tab snapshots are requested asynchronously, with at most one outstanding request per session, and a later explicit Attach cancels an earlier automatic NewTab follow.
- Both WebSocket writers prioritize interactive replies before bulk traffic, with one bulk turn after eight interactive messages to prevent starvation. File start, chunks and completion stay in the same bulk FIFO. Assign encrypted sequence numbers only after the final writer selects a message; reordering already encrypted messages breaks authentication. Keep the final bulk queue bounded to one pending message, and discard revoked sessions before encrypting their queued output. Bytes already written to TCP cannot be overtaken by later input.
- A stopping relay (SIGINT from Fly, SIGTERM from Docker) stops accepting, closes every Mac's link with 1012 and waits at most `SHUTDOWN_GRACE` (3 s, inside Fly's 5 s) before it exits (`announce_restart`). The Mac reads 1012 as a restart (`Ended::RelayRestarting`) and retries every second for `RESTART_WINDOW` (60 s) instead of its doubling backoff, which could otherwise leave it offline for up to 30 s after a deploy's new relay is up. Pages need nothing: their own backoff stops at 5 s.
- Every relay connect is capped by `CONNECT_TIMEOUT`: a local proxy (Stash TUN) can accept TCP and never finish the handshake, which once left the link offline for hours. Bound socket writes and session inbox waits too, but allow short input bursts to wait rather than discard keys. Wrong-key close 4403 is final; idle unauthenticated sessions expire with 4408. A host replacement closes browsers independently of the old data queue, with late input discarded until the close writer finishes.
- The default relay uses `r.kaku.fun`; its browser page lives at `t.kaku.fun/{id}/`, and the relay redirects older `/{id}/` and `/t/{id}/` page links there. Never shorten the 128-bit identity or put a pairing secret in a URL path/query. The page erases the fragment at once and saves the device only after Kaku admits it; when IndexedDB is unavailable it pairs for that tab only and says so. Loopback tokens stay tab-only in sessionStorage. Keep pairing instructions in the CLI, page messages and public docs consistent.
- One identity per Kaku, persisted at `DATA_DIR/remote-share.json` (0600), devices at `remote-devices.json`. `kaku remote --reset` replaces the identity and forgets every device; the running bridge notices within seconds and re-registers.

## Remote Verification

- For an authorized relay deployment, run `fly deploy . --config crates/kaku-relay/fly.toml --dockerfile crates/kaku-relay/Dockerfile --remote-only --depot=false --ha=false --strategy immediate` from the repository root (the build context must reach the page files; the root `.dockerignore` sends only what the relay embeds, about 1 MB, never `target/`). Use `--depot=false` when Depot stalls at builder authentication. Verify the Fly tunnel with `fly doctor` first; do not add `--wg=false` to a working tunnel, since the legacy builder's HTTPS path can fail with an h2c upgrade HTTP 500. This selects a build transport, not a system proxy setting. Verify the deployed image digest, then run `python3 scripts/relay_smoke.py` (a throwaway Mac identity against `wss://r.kaku.fun`: health, status, the page redirect, data both ways with its round trip, 4403/4409/4429 passing through to the page and a foreign `Origin` closed with 4426; it never touches a real Mac or pairing, and point it at a local relay with `ws://127.0.0.1:<port> --origin ''`), and an isolated encrypted session afterward; a dashboard without new releases does not diagnose a failure before image creation. If CLI DNS checks warn while HTTPS works, compare public DNS before changing anything.
- Relay usage: the relay logs `in use: N Macs, M browsers (K paired)` every 10 minutes (`USAGE_EVERY`), and `fly logs` keeps about an hour. For history, Fly's Prometheus API (`https://api.fly.io/prometheus/personal/api/v1/query`, header `Authorization: FlyV1 $(fly auth token)`, plain `Bearer` gets 401) has `fly_app_concurrency{app="kaku-relay"}`, the open connections, Macs and browsers together.
- Run `cargo test --locked -p kaku-remote`, relay tests via its own manifest, and the workspace check/tests/clippy, which build the feature by default as CI does.
- `node --test crates/kaku-remote/tests/web.test.cjs` uses Playwright Chromium to exercise the shipped HTML and xterm, including input privacy, reconnect, upload pacing, history selection, and viewport boundaries. Set `NODE_PATH` when Playwright is installed outside the checkout; `PLAYWRIGHT_CHROMIUM_EXECUTABLE` optionally selects an existing browser. The page draws with WebGL when it can, so most tests launch with WebGL off and read the DOM fallback, and one test checks the WebGL grid, down to its text pixels. After a glyph-page merge the page calls the addon's `setAtlas` before redrawing: the addon uploads a texture slot only when its page's version differs from the slot's last upload, a merge moves pages between slots, and versions repeat (every merged page starts at 1), so a slot kept another page's glyphs. Such a slot is wrong in every frame alike, so the merge test also reads each slot the addon counts as uploaded back once at the end and compares it with its page (red on the old page in 5 of 5 runs where the frame check passed); reading back during the switches made Helium draw a wrong frame by itself now and then. The WebGL tests launch with `GPU_ARGS` (`--use-angle=metal --enable-gpu --ignore-gpu-blocklist`), which give headless Helium WebGL2 on the Apple GPU (2026-10-21; without them it had none and those tests skipped). CI's Chromium can still lack WebGL2 and skip them, so read the reported skips before claiming GPU coverage. Playwright's own Chromium downloads fail code signing on Darwin 27 and its headless shell only has SwiftShader, whose WebGL timings are meaningless. CI's runner is several times slower than a Mac, so a test reads only state it has waited for: the fixture hands the page its config through the socket so the page counts itself connected, `showPicture` waits for the frame's ack, pairing checks wait for the device store. That headless shell at 10x CPU throttling (`Emulation.setCPUThrottlingRate`) reproduces CI's timing failures, the WebGL merge one included (2026-10-25). Helium reloads the first page a fresh profile opens about 0.8 s in, so put a cheap test ahead of a single one run there. Never emulate `deviceScaleFactor` for WebGL checks or measurements: it changes `devicePixelRatio` but not `devicePixelContentBoxSize`, so xterm sizes its canvas at half the device size and draws nothing or a shrunken grid, a failure real browsers do not have.
- The bar for the page (maintainer, 2026-10-16) is how typing, scrolling, copying and tab operations feel: no delay, no stutter, like the app. After changing the page, `web.rs` or the relay, run `node crates/kaku-remote/tests/feel.cjs` (same setup as `live.cjs`) and compare: on loopback, keystroke to echo p50 about 5 ms, a 54-character burst intact, no scroll frame over 25 ms, copy-on-select exact within a frame, new tab shown in about 15 ms, switch and close within one frame (16 ms). It times operations in the page from the click event to the screen change, since Playwright waits about two frames before it clicks. It explicitly disables WebGL with `--disable-webgl` and `--disable-3d-apis`; these are DOM timings, not GPU timings. Headless Helium has WebGL2 only with `GPU_ARGS` from `web.test.cjs`, so WebGL timings need those flags or a headed browser; do not read a DOM-only run as WebGL coverage.
- `node crates/kaku-remote/tests/static_page.cjs` (same app and relay setup as `live.cjs`) also reads DOM rows and explicitly disables WebGL. `--disable-gpu` alone still exposes WebGL2 in some Chromium builds, so it does not guarantee DOM rows exist; use `--disable-webgl` and `--disable-3d-apis` for every DOM-based harness. Keep WebGL off in harnesses that open several tabs for a second reason: headless Helium on Metal stops opening new tabs once a page has drawn with WebGL (navigations abort before any request reaches the server and `newPage` hangs), which looked like a page bug for two rounds.
- After `make app` and a debug relay build, run `node crates/kaku-remote/tests/live.cjs`. It launches only its own app, temporary HOME, and loopback relay, tests encrypted input, uploads across reconnect, frame flow control, host replacement, stable split targets and AlwaysPrompt pane closing, foreign `Host` refusal, and replayed, misplaced and old-format messages, then removes its own fixtures. Never substitute a real share link. DOM-row assertions in `live.cjs` explicitly disable WebGL; real GPU rendering remains covered by the separate browser tests, which must assert canvas output rather than DOM rows.
